# S4 — Gmail API send from an unverified app

- **Dates:** started 2026-10-05; day-8 token check run 2026-10-14 (links checked the same day)
- **Question:** Can organizers connect Gmail and send via the Gmail API before Google verifies the app? What do consent screens, scope classification, refresh-token lifetime and daily limits look like? (spec §8, §9, §13)
- **Result:** **PASS.** An organizer can connect Gmail and send through the Gmail API while the app is unverified. Production must use publishing status **In production**: its refresh token still worked on day 9, while the Testing token had expired.

## Setup

- Google Cloud project `tapnshow` (no billing). Gmail API enabled.
- Google Auth Platform → Audience: External. Day 0 ran with publishing status **Testing** (owner's Gmail as test user), then the same evening with **In production** (still unverified).
- Data Access: `https://www.googleapis.com/auth/gmail.send` → listed under **sensitive scopes** (owner report) — consistent with Google's Gmail scope docs.
- OAuth client: Web application, redirect URI `http://127.0.0.1:53682/callback` (a first attempt failed with `redirect_uri_mismatch` until the URI was registered exactly).
- Throwaway scripts (git-ignored `spikes/s4-gmail/`, not merged): loopback consent with `access_type=offline`, `prompt=consent`; send via `gmail.users.messages.send`.

## Evidence (day 0, 2026-10-05)

- **Testing:** consent completed; token saved with `refresh_token` present, `refresh_token_expires_in=604799` (7 days) and `scope=https://www.googleapis.com/auth/gmail.send` only.
  Send using only the refresh token: `SENT id=1a10b3397151d983` at 2026-10-05T08:34:52Z; delivered to the inbox ("TapNShow S4 spike").
- **In production (unverified):** a second, non-test Google account consented at 2026-10-05T19:02Z through **Advanced → Go to tapnshow (unsafe)**. The token has `scope=https://www.googleapis.com/auth/gmail.send` only and **no** `refresh_token_expires_in`. Send: `SENT id=1a10d7202afe99f7`.
- The consent screen (screenshot kept locally, not committed because it shows both accounts' addresses) reads: *"TapNShow wants access to your Google Account"* with the warning *"This app hasn't been verified by Google. Because this app is requesting some access to your Google Account, you should continue only if you know and trust this app developer."*, then *"You can let the app developer (…) know that they need to submit a request to have this app verified by Google."*

Both outcomes match Google's documented behavior (below).

## Documented limits

- Gmail Help, ["Limits for sending & getting mail"](https://support.google.com/mail/answer/22839): a regular Gmail account hits a limit at "more than 500 recipients in a single email and or more than 500 emails sent in a day".
- Gmail API, ["Usage limits"](https://developers.google.com/workspace/gmail/api/reference/quota): `messages.send` costs 100 quota units; 6,000 units per minute per user per project → **≤ 60 sends per minute per organizer**; "a limit of 500 recipients per email message" still applies.
- Spec §8 quota: organizer Gmail **500 emails/day**; dispatcher must throttle to **≤ 60 sends/min per organizer**.

## Verdict

Google's OAuth docs ([Using OAuth 2.0 → Refresh token expiration](https://developers.google.com/identity/protocols/oauth2#expiration)): *"A Google Cloud Platform project with an OAuth consent screen configured for an external user type and a publishing status of 'Testing' is issued a refresh token expiring in 7 days, unless the only OAuth scopes requested are a subset of name, email address, and user profile."* `gmail.send` is not such a scope, so **Testing status cannot serve real organizers** (connections would break weekly). Production must run with publishing status **In production** (unverified until M9: "unverified app" screen + 100-new-user cap).
